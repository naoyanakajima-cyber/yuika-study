# PdM: 保護者確認モードの検証境界を確定する

担当: pdm_parent_test_scope。正本lease `cycle-20261112T060726Z` / `3bb1b84`、製品基点 PR #25 `042c55dd04a285277dc3dfa9dd296f161283e809`。docs/agent-team.md、ops/AGENTS.md、board.json、前回runと独立QA、現行parent_modeテストと通知clientを読み取り。テスト・製品変更・pushは未実施。

## 目的・今回の範囲

保護者が復習を試す際に本人の記録を変えず通知もしないことを、準備段階と混同せず検証する。前回の初回模擬通知要求1件と単独再試行成功の差を、既存PR内で切り分ける。新機能・外観変更や全体suiteの反復は範囲外。新CEO返答/権限拡張は取り込まない。

現行テストは通常アプリを開いた後に合成通知設定・pending jobを投入し、続いて保護者モードへ遷移する。clientはmount/online/visibilitychangeでflushする。従って準備中の通常動作とモード内の動作を区別する必要がある。ただし、この静的な経路や意図的な準備中flushの再現だけでは、記録のない前回失敗の直接原因を証明したことにならない。

## 受入条件

1. 合成データ・mock API・新規contextのみ。記録するのは準備/入場/モード内/終了後の段階、URL、モード状態、合成要求種別等の必要情報に限定する。実宛先・token・実記録は扱わない。
2. 準備中の通常アプリがpendingを送信し得るかと、保護者モード内で要求が起こるかを独立に確認する。最初の失敗に段階ログがない事実を残す。
3. テスト準備の競合を示す根拠が得られた場合は、通常アプリの通知処理を起動しない同一originの準備ページ等でfixtureを投入し、最初のアプリ起動を保護者モードにする方法を優先する。pendingは入場前から存在させる。
4. callsを途中で消す、要求を無視する、assert/CSP/通知監視を弱める対応はしない。修正ハーネスは入場から終了前まで要求0、本人の合成raw/設定/pending不変、保護者sandboxでの回答・再読込・単元移動を維持する。終了後の通常mock通知が通る正の対照も維持する。
5. モード内で実際に要求が起きる場合だけ製品runtime修正へ進む。準備競合だけならテスト修正に限る。既存の採点/保存キー/形式/出題/通知設定は変更しない。
6. 別担当QAが固定candidateの差分と必要なparent_mode/通知境界の重点試験を確認する。全体suite成功へ読み替えない。前回20/21と今回の結果、実機Safari未検証を分ける。同じ原因の試行は2回まで。

## 終了条件・次の価値

再現経路、変更の必要性、固定commitの検証結果、残る不確実性を同じREV-RECONCILE/既存PR #25へ保存する。根拠が不足なら原因未確定として具体的な次の観測条件を残す。今回は本番採用の判断を求めず、自律範囲内の検証信頼性を整える。修正後は苦手復習の具体的な試用・使い勝手確認を優先し、合成教材追加を次順位、テーマ拡張を低優先とする。承認待ち3件に追加draft2件があるため新規製品PRは増やさない。
