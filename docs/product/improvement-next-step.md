# 次の改善：日次練習の件数表示と合成教材の試し解き

状態：PrM範囲確認済み、技術照合・独立レビュー待ち。製品未実装。
対象チケット：REV-RECONCILE。既存の要件整理権限で進める文書成果。

## 目的と提案の訂正

学習者が始める前に今回の問題数を把握できることを最優先にする。
先に提示した「今日の3問」という新しい入口は、mainの「今日の5問」と重なる。
新しい日次選定は作らず、既存の選定・保存を保って表示の整合を改善する案へ絞る。
3問が継続に有効かは未検証で、既存設定へ追加する根拠にはしない。

利用者から改善提案を求める発言を直接読んだが、提案の採用返答ではない。
CEOの新たな採用・マージ・公開承認は取り込まない。D02の保存先・実接続は未決。

## 優先順位

1. 固定HEADの既存PR #10/#11/#12とmainの対応表を作り、既存の価値と不足を分ける。
2. 日次練習の表示件数と実出題数の整合を最小の製品改善候補とする。
3. 確認済み合成教材をメモリ内だけで試し解きする要件を具体化する。
4. テーマは共通デザインとの共存を確認するまで低優先。新テーマを追加しない。

## 日次練習の受入条件案

対象候補は社会の生成元 `scripts/practice/adaptive.js` と生成先の応仁・鎌倉・平安。
理科 `scripts/practice/science.js`、重点復習、トップ `index.html` の表現も照合対象とするが、
一括変更を暗黙の実装範囲にしない。各画面が既に許容する問題数・保存形式を維持する。
`embed.py`は重点復習も生成する。実装前に4出力すべてを対象にするか設計を再確認し、
生成元と生成物が不一致になるような部分反映は行わない。理科は5/10のみで15を追加しない。

- 開始前の「今回 n 問」と実際の出題数が一致する。選択数より候補が少なければ候補数を表示する。
- 既存の日次選定の期限到来→弱点→通常、フィルター、重複除去を維持。#10のおすすめ方式へ置き換えない。
- 0候補は「この条件では候補がありません」と開始不可にする。記録読取不能・時刻異常とは区別し、既存の停止条件を弱めない。
- 表示更新のために選定用乱数を消費して問題順を変えない。表示と開始の間に別タブ更新があれば、開始時の最新計画を基準に件数を示す設計を先に確定する。
- 初期設定、既存問題数、問題ID・問題版・イベント形式・保存キーを維持。開始だけで回答履歴を増やさない。
- 合成の候補0/1/4/5/9/10/14/15と各画面で有効な設定数、通常/漢字/読み、親モード、保存拒否を検証計画に含める。
- 768×1024で表示→開始→回答→採点→保存→再読込を検証し、通知を遮断。実機Safariや本人の試用は別の未検証事項として残す。

今回のコード照合・限定probeは製品の受入テスト成功ではない。実装後の独立QAが必要。

## 次に独立して進める要件整理

CONTENT-MVPの既存仕様へ「確認済みの合成案を保存せず試し解き」の契約を追記する候補を準備する。
親役が現在revisionの全問を確認し、未解決箇所0のときだけ明示操作で開始する。
読込JSONのconfirmedだけでは開始できず、編集・再入力で確認を失効させる。
text/choiceの採点・正規化、回答前の正答非表示、終了/再読込で回答消去、戻って編集する遷移、
文字列の安全表示、全storage非書込を具体的な合成例で定義する。
未解決画像fixtureを無理に成功経路へ使わず、解決済みの合成画像例を別途用意する。

次回はPdMがこの契約の未確定点を詰め、PrM確認→独立レビューで文書成果まで進められる。
これは追加実装枠ではない。製品待ちは #10/#11/#12 の3件、追加既存draft #22を維持し、新しい製品PRは作らない。
既存PRでの具体的修正に進む場合も、該当PRの目的と基点・互換性・必要テストを先に確定する。
