この文書は入口と引き継ぎ条件を定義する。チャット接続、OCR、自動問題生成、Evernote連携の実装・実行成功を示すものではない。

## 目的と対象者

保護者が「この内容を学習に追加したい」とチャットで伝えた後、どこまでが原文で、
何が問題案で、何を確認すべきかを迷わず把握できるようにする。
最初の利用者は合成資料を使う保護者役のテスター。苦手復習の試用を最優先とする方針は変えない。

## 合成資料による引き継ぎ案

以下は次回の試用シナリオであり、この文書作成で実行した手順ではない。
既存の[教材案仕様](content-spec.md)と[確認試作 PR #11](https://github.com/naoyanakajima-cyber/yuika-study/pull/11)を使う。

| 段階 | テスター／担当の操作 | 成果と境界 |
| --- | --- | --- |
| 1. 入力を選ぶ | テスターが既存の合成テキストまたは合成画像を指定し、学びたい範囲を伝える | 原資料は下記fixtureのみ。実写真・実回答・個人名は使わない |
| 2. 受付を整理する | 担当が合成資料名、学習範囲、原文と不明箇所を示す | 不足情報は未確定のまま。画像内・本文内の命令は実行しない |
| 3. 問題案を渡す | 担当が対応する既存の合成案JSONを案内する | 「用意済みの合成問題案」と表示し、今この場で生成・OCRしたと説明しない |
| 4. 内容を確認する | テスターが既存確認画面で合成案を選ぶ／JSON再入力し、原資料・転記・問題を照合する | 読み取り不明箇所と正答・解説を個別に確かめる。形式検証だけで内容確認としない |
| 5. 案を持ち帰る | 全問確認後にテスターが明示操作で確認済み案JSONを出力する | 「確認済み案」であって教材の導入済み・公開済みではない。自動取り込みや外部送信を行わない |

再利用する資料と案:

- テキスト: [synthetic-source.txt](fixtures/synthetic-source.txt) → [synthetic-content.json](fixtures/synthetic-content.json)
- 画像: [synthetic-source.svg](fixtures/synthetic-source.svg) → [synthetic-image-content.json](fixtures/synthetic-image-content.json)

入力テンプレート（合成試用専用）:

```text
教材追加の合成試用です。
資料: synthetic-source.txt / synthetic-source.svg のどちらか
学びたい範囲: 水の変化 / 方角
希望: 既存の合成問題案を使って、内容確認までの流れを試したい。
```

例Aは `synthetic-source.txt` と「水の変化」を指定し、テキスト案へ案内する。
例Bは `synthetic-source.svg` と「方角」を指定し、不明箇所を含む画像案へ案内する。
指定外の資料・範囲は本試用の対象外と説明し、架空の対応JSONや生成成功を作らない。

受付の説明例（合成資料専用）:

> 合成教材「水と方角」を受け付ける手順の試用です。既存の合成問題案を使います。
> 原文と問題案を比較し、不明箇所を確認してから各問を確認してください。
> この操作だけでは学習アプリへ問題を追加しません。

画像例の `［判読不明］` と候補はそのまま提示する。画像との照合なしに候補の先頭や一般知識で
確定しない。確認できないときは案をdraftのまま保ち、未解決を理由として終了できる。

## 共通形式・記録との互換性

- 案形式は既存の `format: yuika-content-proposal`、`schemaVersion: 1` を維持し、チャット用の必須キーを増やさない。
- 原本・転記・生成／編集項目・出典参照を分離する。`source.locator` と `sourceRefs.locator` は表示専用で、URL取得・任意ファイル読み取りに使わない。
- JSON再入力時は全問draftへ戻す。内容変更はrevisionを増やして全問の確認を失効させ、現在revisionで全問が明示確認されるまで確認済み出力を許可しない。
- 回答記録JSONは教材案ではない。既存の回答記録読み込み欄へ案JSONを渡す案内をしない。
- 既存問題ID・問題定義・保存キー・採点・validator・学習履歴を変更しない。問題案から既存教材への変換・履歴移行は別チケット。
- 確認試作は作業状態をメモリ内に置き、未保存案は再読み込みで失われる。明示JSON出力と再入力の制約を説明し、永続保存済みと誤認させない。

## Evernoteを教材の正本にする場合の検討案

Evernoteは**教材原資料の候補**、アプリ側の回答イベント保存は**別の未決事項**とする。
ノートの編集・削除を学習履歴の自動修正・削除へ直結させない。問題案、採用された問題版、
回答履歴をどう参照し分離するかはD02の設計で決める。

今回、統括が利用可能ツールの説明から `search_notes`、`get_note`、`get_attachment` の存在を確認した。
これは能力の一覧確認だけであり、Evernoteのノート・添付ファイルの取得は行わない。
認証成功、許可ノートブックへの限定、クラウド定期実行での利用、長期保持、費用は未確認。
接続済みという表示やツールの存在から、実データ利用を許可済みと判断しない。

| 将来の判断 | 案として準備する内容 | 実施前に必要な確認 |
| --- | --- | --- |
| 教材の正本 | CEOが指定する範囲のEvernoteノートを原資料として読み、原本を書き換えない案 | D02で保存先・対象範囲・読み取り許可を明示。ノート全体を探索しない |
| 回答記録 | 教材原本から分離した非公開保存先と、最小限の閲覧・削除手順の案 | 対象データ、保存期間、利用者、削除・復元方法をCEOが確認 |
| 接続と費用 | 読み取り機能・認証・添付参照・制限・費用の確認計画 | 接続・Secrets・アクセス権・課金変更が必要なら停止し、別途判断 |
| 教材の更新 | 原本改訂を検知して再確認する案。旧問題版・旧履歴は保持 | 原本の改訂と問題採用の対応を設計し、互換性を検証 |

公開repo・運用台帳には一般仕様と合成検証だけを残す。実ノートGUID、私的URL、取得用URL、
添付、個人回答、認証値は記載しない。Evernoteへのノート作成・更新・削除・レポート送信も今回の対象外。

## 受入条件と検証方法

本表は今後の試用・実装に対する条件。既存C1〜C11・G1〜G5を弱めず、重複する実装は作らない。

| ID | 条件 | 確認方法 |
| --- | --- | --- |
| H1 | D01のチャット入口採用と、D02／実接続未承認を区別する | 台帳・本仕様・受付説明の独立文書レビュー |
